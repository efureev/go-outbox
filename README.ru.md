**Ваше приложение пишет сообщение в той же транзакции, что и бизнес-изменение.
Этот сервис его доставляет — в RabbitMQ, в Kafka, в несколько инстансов сразу — и
не теряет.**

Диспетчер паттерна Transactional Outbox: сайдкар, который читает таблицу в БД и
публикует найденное. Ни клиентской библиотеки для встраивания, ни фреймворка для
внедрения — в приложении не появляется ничего, кроме одного `INSERT`.

## Почему именно он

- **Ничего не теряется.** Строка становится `sent` только после подтверждения от
  брокера — publisher confirm в AMQP, `acks=all` в Kafka. Не в момент, когда байты
  ушли из процесса.

- **Масштабируется вширь и безопасно.** Запускайте сколько угодно реплик на одной
  таблице. Захват идёт через `FOR UPDATE SKIP LOCKED` и несёт lease-токен, который
  обязана предъявить любая запись результата, поэтому реплика с истёкшим lease не
  может перетереть то, что уже доставила другая. Это обеспечено схемой, а не
  соглашением.

- **Быстро, и это можно перепроверить.** ~7 800 msg/s через RabbitMQ с включёнными
  подтверждениями; ~12 000, если поднять воркеры и пул каналов вместе; ~46 000, если
  убрать брокер из картины, — сам диспетчер узким местом не становится. `make bench`
  воспроизводит каждую цифру на вашем железе.

- **Миллисекунды, а не интервалы опроса.** Триггер будит пайплайн в момент записи
  строки — ~105 мс сквозняком на дефолтах и ~5 мс, если убрать окно debounce и
  разброс между репликами. Polling остаётся включённым как сверка, поэтому
  потерянное уведомление стоит одного интервала и никогда — сообщения.

- **Много брокеров одновременно.** Четыре стрима на трёх инстансах RabbitMQ плюс
  кластер Kafka — это конфигурация, а не форк. Продюсер выбирает направление одной
  колонкой, и у каждого стрима свой пайплайн, поэтому упавший в процессе работы
  брокер задерживает только адресованные ему стримы. (На старте доступны должны быть
  все: недоступный роняет запуск, а не поднимает половину диспетчера.)

- **Восстанавливается сам.** Убитая посреди батча реплика оставляет строки под
  lease; lease истекает, и их забирает другая. Штатная остановка не ждёт даже
  этого — она сразу возвращает незавершённые захваты в очередь.

- **Авария стоит задержки, а не вечера.** Бюджет повторов считает, сколько раз
  брокер *отверг* сообщение. Недоступный брокер его не видел и потому ничего не
  тратит: сообщение ждёт и уходит, когда брокер вернётся, — сколько бы это ни
  заняло. Никакой таблицы `failed`, которую надо руками возвращать в очередь
  после двадцатиминутного перезапуска.

- **Говорит, что произошло.** 20 метрик Prometheus, включая ту единственную, которая
  действительно важна: сколько ждёт самое старое недоставленное сообщение. Упавшие
  сообщения можно посмотреть и вернуть в очередь по HTTP — писать `UPDATE` руками не
  придётся никому.

- **Виден внутри трейса.** Укажите коллектор OpenTelemetry — и каждое сообщение
  получит спан `outbox.publish` между спанами продюсера и консьюмера, так что
  ожидание между коммитом строки и передачей её брокеру перестанет быть числом,
  которое никто не может объяснить. По умолчанию выключено, и выключенное не
  стоит ничего: ни экспортёра, ни спана, ни аллокации.

- **Скучен в эксплуатации.** Образ `scratch` на 29 МБ без шелла и пакетного
  менеджера — или статический бинарник. Доставленные строки вычищаются по заданному
  сроку хранения. Десять прямых зависимостей, ни веб-фреймворка, ни DI-контейнера.

- **Падает на старте, а не в три часа ночи.** Вся конфигурация читается и
  проверяется до того, как что-либо подключится, и все проблемы выводятся вместе —
  неверный порог, опечатка в ключе драйвера, три драйвера без DSN, — так что на
  диагностику уходит один перезапуск, а не по одному на каждую ошибку.

- **Доказано, а не заявлено.** 194 теста, половина — против настоящих PostgreSQL,
  RabbitMQ и Redpanda: набор правил конкурентности, выраженных в SQL, нельзя
  проверить моком, сверяющим текст запроса.

## Установка

### Образ контейнера

```bash
docker pull ghcr.io/efureev/go-outbox:1.0.0
```

Публикуется на каждый тег для `linux/amd64` и `linux/arm64`. Теги: точная
версия, минорная линия (`1.0`) и `latest`; предрелиз последние два не двигает.
Образ — это `scratch` плюс набор корневых сертификатов: ни шелла, ни пакетного
менеджера, ничего, чем мог бы воспользоваться попавший внутрь.

### Бинарник

Готовые архивы для Linux и macOS, amd64 и arm64, на
[странице релизов](https://github.com/efureev/go-outbox/releases):

```bash
VERSION=1.0.0
curl -fsSLO "https://github.com/efureev/go-outbox/releases/download/v$VERSION/outbox_${VERSION}_linux_amd64.tar.gz"
curl -fsSLO "https://github.com/efureev/go-outbox/releases/download/v$VERSION/SHA256SUMS"
sha256sum --check --ignore-missing SHA256SUMS

tar -xzf "outbox_${VERSION}_linux_amd64.tar.gz"
sudo install -m 0755 "outbox_${VERSION}_linux_amd64/outbox" /usr/local/bin/outbox
outbox version
```

Бинарник статический: ни рантайма ставить, ни libc подбирать не нужно.

### Через Go

```bash
go install github.com/efureev/go-outbox/cmd/outbox@latest
```

Удобно, но версия при этом не штампуется — `outbox version` покажет `dev`. Там,
где важно знать, что именно развёрнуто, берите архив релиза или образ.

### Из исходников

```bash
git clone https://github.com/efureev/go-outbox.git && cd go-outbox
make build              # ./bin/outbox
make image              # локальный образ контейнера
make dist               # архивы релиза под все платформы
```

## Быстрый старт

```bash
docker compose up -d                       # PostgreSQL, RabbitMQ, Redpanda
cp .env.example .env
go run ./cmd/outbox migrate up
go run ./cmd/outbox run
```

Записать сообщение так, как это делает продюсер:

```sql
INSERT INTO outbox.messages (id, stream, topic, payload, target)
VALUES (gen_random_uuid(), 'local', 'orders.placed',
        '{"order":"A-1"}'::text::bytea, '{"key":"customer-1"}'::jsonb);
```

или из Go — в той же транзакции, что несёт бизнес-изменение:

```go
client := outboxclient.Default()

tx, err := pool.Begin(ctx)
if err != nil {
    return err
}
defer tx.Rollback(ctx)

if _, err := tx.Exec(ctx, `UPDATE accounts SET balance = balance - $1 WHERE id = $2`, amount, id); err != nil {
    return err
}

if err := client.Enqueue(ctx, tx, outboxclient.Message{
    Stream:  "local",
    Topic:   "account.debited",
    Payload: payload,
    Headers: map[string]string{"traceparent": traceparent},
}); err != nil {
    return err
}

return tx.Commit(ctx)
```

## Как это работает

```
транзакция продюсера                  go-outbox                     брокер
┌────────────────────┐        ┌────────────────────────┐        ┌─────────┐
│ UPDATE accounts …  │        │ захват (SKIP LOCKED,   │        │         │
│ INSERT строки      │───────▶│         lease-токен)   │───────▶│ RabbitMQ│
│ COMMIT             │        │ публикация (с подтв.)  │        │  Kafka  │
└────────────────────┘        │ запись результата      │        │         │
                              │  (с проверкой lease)   │        └─────────┘
                              └────────────────────────┘
```

Сообщение продюсера и его бизнес-изменение фиксируются или откатываются вместе.
Ровно это свойство и покупается паттерном; всё остальное здесь нужно, чтобы
выполнить обещание, не потеряв, не продублировав и не подвесив сообщение после
коммита транзакции.

Доставка — **at-least-once**. Реплика может упасть между приёмом сообщения брокером
и записью этого факта в базу, поэтому потребитель обязан быть идемпотентным: для
этого каждое сообщение несёт свой outbox-идентификатор (`MessageId` в AMQP,
заголовок `message_id` в Kafka).

Порядок **не** гарантируется. Реплики публикуют параллельно, воркеры внутри реплики
тоже, а переотправленное сообщение уходит позже написанных после него. Потребителю,
которому нужен порядок в пределах ключа, придётся обеспечить его самому.

Полный контракт, включая то, что осознанно не обещается, — в
[docs/PublicContract.ru.md](docs/PublicContract.ru.md).

## Конфигурация

Каждая настройка — переменная окружения с префиксом `OUTBOX_`. Всё читается на
старте и проверяется до того, как что-либо подключится. Некорректное значение
останавливает процесс, перечисляя **все** проблемы сразу, а не поднимает сервис,
который навсегда останется unready.

```
OUTBOX_DB_DSN=postgres://user:pass@db:5432/app?sslmode=require
OUTBOX_STREAMS=local
OUTBOX_STREAM_LOCAL_DRIVER=rmq
OUTBOX_DRIVER_RMQ_TYPE=rabbitmq
OUTBOX_DRIVER_RMQ_DSN=amqp://user:pass@rabbit:5672/
```

**Стрим** — логическое направление, которое продюсер указывает в строке;
**драйвер** — подключение к конкретному брокеру. Драйверов может быть столько,
сколько брокеров нужно достать: несколько инстансов RabbitMQ, несколько
кластеров Kafka или и то и другое сразу, — а продюсер выбирает между ними одной
колонкой. У каждого стрима свой пайплайн, поэтому лежащий брокер задерживает
только адресованные ему стримы.

Полный справочник: [docs/Config.ru.md](docs/Config.ru.md).

## Эксплуатация

| Эндпоинт | Назначение |
|---|---|
| `GET /health` | Liveness. Зависимости не проверяет. |
| `GET /ready` | Readiness: все модули здоровы. |
| `GET /api/v1/stats` | Размер backlog'а, сконфигурированные стримы и драйверы, настройки. |
| `GET /api/v1/messages/failed` | Постранично: что встало и почему. `?stream=` сужает до одного. |
| `POST /api/v1/messages/requeue` | Вернуть упавшие сообщения в очередь. Требует `OUTBOX_HTTP_ADMIN_TOKEN`. |
| `GET /metrics` (порт 9100) | Prometheus. |

Последние три доступны и подкомандами — `outbox stats`, `outbox failed`,
`outbox requeue`, — которые идут в базу напрямую, а не через под. Вызовы store те
же, авторизация разная: эндпоинтам нужен токен, командам — учётные данные базы.

Возврат упавших сообщений в очередь — из любого места:

```bash
curl -X POST -H 'Authorization: Bearer $TOKEN' \
  localhost:8085/api/v1/messages/requeue \
  -d '{"failed_before":"2026-01-01T00:00:00Z"}'
```

```sql
SELECT outbox.requeue(ARRAY['…']::uuid[]);
```

Метрики, стартовые алерты и дашборд Grafana для импорта
([`dashboards/outbox.json`](dashboards/outbox.json)):
[docs/MetricsAndAlerts.ru.md](docs/MetricsAndAlerts.ru.md).

## Разработка

```bash
make up                 # поднять PostgreSQL, RabbitMQ и Redpanda
make test               # юнит-тесты
make test-integration   # интеграционные тесты на реальной инфраструктуре
make soak SOAK=1h       # те же отказы, под нагрузкой, сколько захотите
make bench              # цифры, приведённые в changelog
make lint               # golangci-lint в контейнере, версия зафиксирована по CI
make fmt
```

`lint` и `fmt` работают в контейнере, а не с тем, что лежит в `PATH`: линтер,
отличающийся у разработчика и на CI, выдаёт разные результаты — и проявляется
это тем, что зелёный локальный прогон превращается в красный пайплайн. Когда
скорость итерации важнее точного совпадения с CI, есть `make lint-host`,
использующий бинарник из `PATH`.

Основной вес тестового набора намеренно лежит на интеграционных тестах: продукт
представляет собой набор правил конкурентности и владения, выраженных в SQL, а
такие правила нельзя проверить утверждением, что текст запроса не изменился.
