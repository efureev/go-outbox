# go-outbox

[English](README.md) | Русский

Диспетчер паттерна Transactional Outbox. Приложение-продюсер пишет сообщение в
таблицу БД в той же транзакции, что и бизнес-изменение, которое это сообщение
описывает; сервис читает эти строки и публикует их в RabbitMQ или Kafka.

Ровно одно свойство — сообщение и изменение фиксируются или откатываются
вместе — и есть то, ради чего существует паттерн. Всё остальное здесь нужно,
чтобы выполнить это обещание, не потеряв, не продублировав и не подвесив
сообщение после того, как транзакция закоммичена.

```
транзакция продюсера                  go-outbox                     брокер
┌────────────────────┐        ┌────────────────────────┐        ┌─────────┐
│ UPDATE accounts …  │        │ захват (SKIP LOCKED,   │        │         │
│ INSERT строки      │───────▶│         lease-токен)   │───────▶│ RabbitMQ│
│ COMMIT             │        │ публикация (с подтв.)  │        │  Kafka  │
└────────────────────┘        │ запись результата      │        │         │
                              │  (с проверкой lease)   │        └─────────┘
                              └────────────────────────┘
```

## Что гарантируется

- **Доставка at-least-once.** Закоммиченное сообщение рано или поздно будет
  опубликовано. Потребитель обязан быть идемпотентным; для этого каждое
  сообщение несёт свой outbox-идентификатор — `MessageId` в AMQP и заголовок
  `message_id` в Kafka.
- **Публикация с подтверждением.** Строка помечается доставленной только после
  того, как брокер сказал, что сообщение у него: publisher confirm в AMQP,
  `acks=all` в Kafka.
- **Безопасное горизонтальное масштабирование.** На одной таблице может
  работать любое число реплик. Захват выполняется через
  `FOR UPDATE SKIP LOCKED` и получает lease-токен, который обязана предъявить
  любая запись результата. Поэтому реплика, чей lease истёк во время публикации,
  не может перетереть результат, записанный тем, кто эту строку перезахватил.
- **Восстановление без ручного вмешательства.** Реплика, упавшая посреди батча,
  оставляет строки под lease; lease истекает, и строки забирает другая реплика.
  Штатная остановка даже не ждёт истечения — она сразу возвращает незавершённые
  захваты в очередь.

Чего **не** гарантируется — порядок. Реплики публикуют параллельно, а
переотправленное сообщение уходит позже написанных после него. Если потребителю
нужен порядок в пределах ключа, он обеспечивает его сам.

## Быстрый старт

```bash
docker compose up -d                       # PostgreSQL, RabbitMQ, Redpanda
cp .env.example .env
go run ./cmd/outbox migrate up
go run ./cmd/outbox run
```

Записать сообщение так, как это делает продюсер:

```sql
INSERT INTO outbox.messages (id, stream, topic, payload, target)
VALUES (gen_random_uuid(), 'local', 'orders.placed',
        '{"order":"A-1"}'::text::bytea, '{"key":"customer-1"}'::jsonb);
```

или из Go — в той же транзакции, что несёт бизнес-изменение:

```go
client := outboxclient.Default()

tx, err := pool.Begin(ctx)
if err != nil {
    return err
}
defer tx.Rollback(ctx)

if _, err := tx.Exec(ctx, `UPDATE accounts SET balance = balance - $1 WHERE id = $2`, amount, id); err != nil {
    return err
}

if err := client.Enqueue(ctx, tx, outboxclient.Message{
    Stream:  "local",
    Topic:   "account.debited",
    Payload: payload,
    Headers: map[string]string{"traceparent": traceparent},
}); err != nil {
    return err
}

return tx.Commit(ctx)
```

## Конфигурация

Каждая настройка — переменная окружения с префиксом `OUTBOX_`. Всё читается на
старте и проверяется до того, как что-либо подключится. Некорректное значение
останавливает процесс, перечисляя **все** проблемы сразу, а не поднимает сервис,
который навсегда останется unready.

```
OUTBOX_DB_DSN=postgres://user:pass@db:5432/app?sslmode=require
OUTBOX_STREAMS=local
OUTBOX_STREAM_LOCAL_DRIVER=rmq
OUTBOX_DRIVER_RMQ_TYPE=rabbitmq
OUTBOX_DRIVER_RMQ_DSN=amqp://user:pass@rabbit:5672/
```

**Стрим** — логическое направление, которое продюсер указывает в строке;
**драйвер** — подключение к конкретному брокеру. Несколько стримов могут делить
один драйвер, а одна инсталляция — публиковать одновременно в RabbitMQ и Kafka.
У каждого стрима свой пайплайн, поэтому лежащий брокер задерживает только свои
сообщения.

Полный справочник: [docs/Config.ru.md](docs/Config.ru.md).

## Эксплуатация

| Эндпоинт | Назначение |
|---|---|
| `GET /health` | Liveness. Зависимости не проверяет. |
| `GET /ready` | Readiness: все модули здоровы. |
| `GET /api/v1/stats` | Размер backlog'а, сконфигурированные стримы и драйверы, настройки. |
| `GET /api/v1/messages/failed` | Постранично: что встало и почему. |
| `POST /api/v1/messages/requeue` | Вернуть упавшие сообщения в очередь. Требует `OUTBOX_HTTP_ADMIN_TOKEN`. |
| `GET /metrics` (порт 9100) | Prometheus. |

Возврат упавших сообщений в очередь — из любого места:

```bash
curl -X POST -H 'Authorization: Bearer $TOKEN' \
  localhost:8085/api/v1/messages/requeue \
  -d '{"failed_before":"2026-01-01T00:00:00Z"}'
```

```sql
SELECT outbox.requeue(ARRAY['…']::uuid[]);
```

Метрики и стартовые алерты: [docs/MetricsAndAlerts.ru.md](docs/MetricsAndAlerts.ru.md).

## Разработка

```bash
make up                 # поднять PostgreSQL, RabbitMQ и Redpanda
make test               # юнит-тесты
make test-integration   # интеграционные тесты на реальной инфраструктуре
make lint
```

Основной вес тестового набора намеренно лежит на интеграционных тестах: продукт
представляет собой набор правил конкурентности и владения, выраженных в SQL, а
такие правила нельзя проверить утверждением, что текст запроса не изменился.

## Требования

- Go 1.26
- PostgreSQL 13 или новее
- RabbitMQ 3.8+ и/или Kafka 2.4+
