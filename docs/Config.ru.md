# Конфигурация

[English](Config.md) | Русский

Каждая настройка — переменная окружения с префиксом `OUTBOX_`. Значения также читаются из файла `.env`, если он есть;
окружение имеет приоритет.

Всё читается и проверяется на старте. Некорректная длительность или порог вне допустимого диапазона останавливают
процесс, причём выводятся **все** проблемы сразу — так на диагностику неверно настроенного развёртывания уходит один
перезапуск, а не по одному на каждую ошибку.

## Приложение

| Переменная                    | По умолчанию | Смысл                                                                                              |
|-------------------------------|--------------|----------------------------------------------------------------------------------------------------|
| `OUTBOX_APP_NAME`             | `outbox`     | Передаётся в PostgreSQL как `application_name` — именно под ним сервис виден в `pg_stat_activity`. |
| `OUTBOX_APP_ENV`              | `prod`       | Метка окружения.                                                                                   |
| `OUTBOX_APP_INSTANCE`         | hostname     | Записывается в колонку `owner` захваченной строки, чтобы было видно, какая реплика держит lease.   |
| `OUTBOX_APP_SHUTDOWN_TIMEOUT` | `30s`        | Ограничивает всю процедуру остановки.                                                              |

## Логирование

| Переменная          | По умолчанию | Смысл                                                                                                                                                    |
|---------------------|--------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|
| `OUTBOX_LOG_LEVEL`  | `info`       | `trace`, `debug`, `info`, `warn`, `error`, `fatal`, `panic`.                                                                                             |
| `OUTBOX_LOG_FORMAT` | `json`       | `console` для терминала, `text` для плоского `key=value`, `json` для сборщика логов.                                                                     |
| `OUTBOX_LOG_CALLER` | `false`      | Писать место вызова. Полезно при отладке; у зависимостей разрешается в путь внутри кеша модулей Go, который называет версию библиотеки, а не подсистему. |

### Что несёт каждая строка

| Поле        | Смысл                                                                                                                                                                                                      |
|-------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `module`    | Подсистема: `db`, `brokers`, `dispatch`, `janitor`, `metrics`, `http`, `hub`. `grep module=db` возвращает всё об одной подсистеме — и что с ней сделал менеджер жизненного цикла, и что она сделала сама.  |
| `component` | Равно `lifecycle` у собственного логирования фреймворка, которое не принадлежит ни одному модулю. Отдельный от `module` ключ намеренно: такие строки несут атрибут `module`, называющий *объект* действия. |
| `instance`  | Реплика — то же значение, что захват пишет в колонку `owner`, поэтому строка лога и строка таблицы называют один и тот же процесс.                                                                         |

В формате **console** подсистема выводится перед сообщением, а не полем, потому что одно и то же имя дважды в строке —
это шум:

```
15:04:05.128 INF [db] database pool opened instance=outbox-7d9f max_conns=10
15:04:05.130 INF [lifecycle] starting module instance=outbox-7d9f module=dispatch
```

Грепать там нужно `[db]`. В формате **json** префикса нет: сообщение остаётся нетронутым для сборщика, а имя — в поле
`module`.

### Строка, которую читают первой

Как только поднялся весь граф модулей, выводится одна строка с конфигурацией, с которой процесс фактически запустился:

```
15:04:05.128 INF [outbox] ready instance=outbox-7d9f version=1.0.0 streams=global:kfk,local:rmq
    batch_size=200 workers=8 poll_interval=5s lease_ttl=2m max_attempts=5 max_defer=unbounded
    notify=true retention=168h
```

`GET /api/v1/stats` отвечает на тот же вопрос про работающий процесс. Эта строка отвечает на него про уже заменённый — а
при разборе инцидента нужен обычно именно такой ответ.

### Сколько стоит строка лога

Диспетчер **не пишет ничего на сообщение**. Захват, публикация и запись результата не выводят ни строки; наблюдаемость
на этом пути — счётчики Prometheus, которые питаются доменными событиями. Страж-тест прогоняет 100 и 1000 сообщений на
уровне `trace` и падает при расхождении числа строк: `Debug`
внутри цикла публикации выглядит как улучшение и стоит аллокации на сообщение даже при выключенном уровне.

Измерено через `make bench-logging`, на строку, с привязанными `instance` и
`module`:

|                                 | ns/op | аллокаций |
|---------------------------------|------:|----------:|
| `json`, без атрибутов записи    |  ~345 |         0 |
| `json`, три атрибута записи     |  ~445 |         3 |
| `console`, без атрибутов записи |  ~228 |         1 |
| `console`, три атрибута записи  |  ~391 |         4 |
| ниже порога уровня              |   ~15 |         1 |

Привязанные поля кодируются один раз при создании логгера, поэтому `instance` на каждой строке стоит копии памяти, а не
аллокации. Каждый атрибут, переданный на месте вызова, стоит одной аллокации, а префикс в console — ещё одной; поэтому
он и остаётся форматом для разработки.

### Отметки времени

| Формат    | Шаблон                          | Пример                             |
|-----------|---------------------------------|------------------------------------|
| `console` | `15:04:05.000`                  | `15:04:05.128`                     |
| `text`    | `2006-01-02T15:04:05.000Z07:00` | `2026-08-19T15:04:05.128+03:00`    |
| `json`    | RFC3339 с наносекундами         | `2026-08-19T15:04:05.128533+03:00` |

Миллисекунды есть везде намеренно: латентность доставки здесь измеряется именно в них, и отметка времени без них не
позволяет упорядочить захват, публикацию и запись результата.

## Стримы и драйверы

**Стрим** — логическое направление, которое продюсер указывает в строке. **Драйвер** — подключение к конкретному
брокеру. Несколько стримов могут делить один драйвер.

```dotenv
OUTBOX_STREAMS=local,global

OUTBOX_STREAM_LOCAL_DRIVER=rmq
OUTBOX_STREAM_GLOBAL_DRIVER=kfk

OUTBOX_DRIVER_RMQ_TYPE=rabbitmq
OUTBOX_DRIVER_RMQ_DSN=amqp://user:pass@rabbit:5672/

OUTBOX_DRIVER_KFK_TYPE=kafka
OUTBOX_DRIVER_KFK_BROKERS=kafka-1:9092,kafka-2:9092
```

Настройки драйвера ищутся по точному совпадению ключа из закрытого набора. Опечатка в ключе — ошибка на старте, а не
настройка, которая молча ничего не делает. И драйвер, чьё имя является префиксом другого (`rmq` и `rmq_local`), читает
только свои переменные.

### Несколько брокеров одного типа

Драйвер не привязан к *типу* брокера — драйвер это одно соединение, и их может быть столько, сколько брокеров нужно
достать. Четыре стрима на трёх отдельных инстансах RabbitMQ — это четыре блока драйверов, у каждого свой DSN:

```dotenv
OUTBOX_STREAMS=local,test,global,tetra

OUTBOX_STREAM_LOCAL_DRIVER=rmq_local
OUTBOX_DRIVER_RMQ_LOCAL_TYPE=rabbitmq
OUTBOX_DRIVER_RMQ_LOCAL_DSN=amqp://user:pass@rabbit-a:5672/
OUTBOX_DRIVER_RMQ_LOCAL_PREFIX=loc

# …и так далее для rmq_test, rmq_global и rmq_tetra.
```

Два драйвера могут смотреть в один брокер и остаются независимыми: у каждого своё соединение, свой пул каналов и своё
именование. Имена драйверов, различающиеся только `-` против `_`, отвергаются на старте — оба адресуют один и тот же
блок
`OUTBOX_DRIVER_…`.

Разобранный пример со всеми подводными камнями — в
[сценарии 5](UseCases.ru.md#5-четыре-стрима-на-трёх-инстансах-rabbitmq).

### Общее для всех драйверов

| Ключ          | По умолчанию                | Смысл                                                                       |
|---------------|-----------------------------|-----------------------------------------------------------------------------|
| `TYPE`        | —                           | `rabbitmq` (либо `rmq`, `amqp`) или `kafka`. Обязателен.                    |
| `PREFIX`      | —                           | Добавляется к каждому имени топика — чтобы делить брокер между окружениями. |
| `PREFIX_SEP`  | `_` для AMQP, `.` для Kafka | Разделитель между префиксом и топиком.                                      |
| `VERSION_SEP` | `_` для AMQP, `.` для Kafka | Разделитель перед суффиксом `vN`.                                           |

Эффективное имя, на которое должен подписаться потребитель:

```
[prefix + prefix_sep] + topic + [version_sep + "v" + version]
```

то есть при `PREFIX=prod`, топике `user.created` и `target.version = 2`
получится `prod_user.created_v2` в AMQP.

## Пересылка в dead-letter

Когда сообщение перестаёт переотправляться, его можно переслать туда, где его ждёт потребитель. Строка в таблице
остаётся в любом случае: dead-letter-топик — это сигнал, а не сама запись.

| Переменная           | По умолчанию         | Смысл                                            |
|----------------------|----------------------|--------------------------------------------------|
| `OUTBOX_DLQ_ENABLED` | `false`              |                                                  |
| `OUTBOX_DLQ_STREAM`  | —                    | Должен быть одним из сконфигурированных стримов. |
| `OUTBOX_DLQ_TOPIC`   | `outbox.dead-letter` |                                                  |
