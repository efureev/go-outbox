# ТЗ: новые адресаты (веха 1.6)

[English version](DriverSpec.md)

Что нужно сделать, чтобы добавить драйвер, нужен ли каждый из кандидатов и во что обходится размер приложения. Цифры
измерены, а не оценены: предыдущая оценка на [странице роадмапа](Roadmap.ru.md) ошиблась в разы, и повторять это
незачем.

## Сводка

Замерено на linux/amd64, `go build -trimpath -ldflags '-s -w'`, база — тег v1.5.0 (21.87 МБ). Зонд для каждой библиотеки
достижим из `main`, иначе линковщик выбрасывает её целиком и замер показывает ноль.

| Кандидат                 | Бинарник | Прирост      | Модулей | Вердикт                    |
|--------------------------|----------|--------------|---------|----------------------------|
| Клиент на `database/sql` | 21.87 МБ | **0**        | 0       | **Сделано** — `pkg/outboxsql` |
| NATS JetStream           | 23.45 МБ | **+1.58 МБ** | +3      | **Делать**                 |
| SQS                      | 25.11 МБ | +3.24 МБ     | +15     | По запросу                 |
| Redis Streams            | 28.20 МБ | **+6.33 МБ** | +2      | **Не делать без оговорки** |

Порядок в роадмапе стоит поменять. Он ставил NATS первым, Redis вторым; по факту Redis стоит вчетверо дороже NATS, а
гарантию доставки даёт слабее всех четырёх. Клиент на `database/sql` бесплатен для демона и по этой причине должен идти
впереди всего.

Прирост образа равен приросту бинарника: образ на `scratch` не содержит ничего, кроме бинарника и корневых сертификатов.
То есть Redis Streams увеличили бы образ с 29 МБ до 35 МБ — на 22% ради брокера, чья долговечность слабее той, что
диспетчер обещает.

## Что вообще требуется от драйвера

Контракт один, в [`internal/broker/broker.go`](../internal/broker/broker.go):

```go
type Publisher interface {
Publish(ctx context.Context, msgs []core.Message) []error
HealthCheck(ctx context.Context) error
Close(ctx context.Context) error
}
```

Позиционный срез ошибок — не украшение: одно плохое сообщение не должно обрекать на повтор весь батч. Каждая ошибка
попадает в один из трёх классов, и это самое важное решение в любом драйвере:

| Класс              | Что значит                             | Что делает диспетчер                               |
|--------------------|----------------------------------------|----------------------------------------------------|
| `core.Permanent`   | брокер посмотрел и отказал навсегда    | сразу в `failed`, попытки не тратятся              |
| `core.Unavailable` | до брокера не достучались              | обратно в `pending`, **счётчик попыток не растёт** |
| любая другая       | брокер отказал, но повтор может помочь | backoff, попытка тратится                          |

Ошибиться в сторону `Unavailable` дороже всего: сообщение с личной проблемой, принятое за аварию, никогда не увеличит
счётчик и потому никогда не дойдёт до
`failed`. Всё, что не опознано как недоступность положительно, остаётся retryable.

## 1. Клиент продюсера на `database/sql`

**Сделано** — [`pkg/outboxsql`](../pkg/outboxsql), рецепт в
[сценарии 6](usecases/6-database-sql.ru.md). Ниже — то, что было в ТЗ,
оставлено ради обоснования.

**Нужен: да, и первым.** Ноль стоимости для демона, и это единственный пункт вехи, расширяющий не список брокеров, а
список тех, кто вообще может писать в outbox.

**Размер: +0 МБ.** Проверено: демон не импортирует `pkg/outboxclient`
(`go list -deps ./cmd/outbox` не содержит его), поэтому клиент не линкуется в бинарник вообще — ни сейчас, ни после.

### Задача

`pkg/outboxclient` требует pgx:

```go
type Execer interface {
Exec(ctx context.Context, sql string, args ...any) (pgconn.CommandTag, error)
}
```

Это отсекает всех, кто работает через `database/sql`, `sqlx` или `gorm`: у них
`ExecContext` возвращает `sql.Result`, а не `pgconn.CommandTag`.

### Ключевое ограничение

**Новый клиент обязан лежать в отдельном пакете.** Если положить его в
`pkg/outboxclient`, импорт этого пакета продолжит тянуть pgx — то есть выгода, ради которой всё затевалось, исчезнет.
Предлагается `pkg/outboxsql`.

### Спецификация

```go
package outboxsql

// Execer — то, что даёт database/sql. Ему удовлетворяют *sql.DB, *sql.Tx,
// *sqlx.DB и *sqlx.Tx; передача транзакции — весь смысл.
type Execer interface {
	ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
}

func New(schema, table string) (*Client, error)
func Default() *Client
func (c *Client) Enqueue(ctx context.Context, db Execer, msg Message) error
func (c *Client) EnqueueBatch(ctx context.Context, db Execer, msgs []Message) error
```

- SQL и валидация идентификаторов переиспользуются как есть: плейсхолдеры
  `$1…$n` одинаковы у pgx и `lib/pq`, поэтому текст запроса не меняется.
- `Message` и `Target` дублируются, а не импортируются из `outboxclient`:
  импорт вернул бы pgx в граф.
- `EnqueueBatch` — это `ExecContext` в цикле внутри транзакции вызывающего, а не
  `pgx.Batch`. Один round trip на сообщение вместо одного на батч; это цена совместимости, и её надо назвать в
  документации.

### Что проверить обязательно

**Кодирование `JSONB`.** Измерено, а не предположено: и `[]byte`, и `string`
доезжают до колонки `jsonb` целыми через `lib/pq` и через `pgx/v5/stdlib`, а
payload из произвольных не-UTF8 байт проходит через `bytea` кругом у обоих.
Реализация всё равно передаёт JSON-колонки как `string`: `[]byte` — та форма,
которую драйвер вправе закодировать как `bytea`, а пакет не знает, с каким
драйвером говорит. Оба драйвера покрыты интеграционными тестами.

### Тесты

- Интеграционный: вставка через `database/sql` + `lib/pq`, затем чтение той же строки через `Store.Claim` — то есть
  демон видит написанное чужим клиентом.
- То же через `pgx/v5/stdlib`, потому что это самый вероятный способ использования.
- Круговой тест на `headers`/`target`: непустой JSON доезжает до брокера неизменным.

## 2. NATS JetStream

**Нужен: да.** Из трёх брокеров-кандидатов JetStream ложится на контракт диспетчера лучше всех, и стоит дешевле всех.

**Размер: +1.58 МБ** (23.45 МБ), три модуля: `nats.go`, `nkeys`, `nuid`.

### Почему ложится хорошо

`js.PublishMsg(ctx, msg)` возвращает `*jetstream.PubAck` — синхронное подтверждение от стрима на каждое сообщение. Это
ровно то, чего требует диспетчер: строка становится `sent` только после того, как брокер сказал, что сообщение у него.
Ни машинерии отложенных подтверждений, как в AMQP, ни раскладывания батча по позициям, как в Kafka. Драйвер получается
самым простым из трёх.

Отдельная выгода, которой нет у остальных: **дедупликация на стороне стрима**. JetStream отбрасывает повтор с тем же
`Nats-Msg-Id` внутри окна
`duplicate_window`. Id строки outbox ложится туда напрямую, и повторная публикация после перезапуска реплики перестаёт
быть дубликатом *в стриме* — при том что доставка по-прежнему at-least-once. Это стоит записать в публичный контракт как
преимущество конкретного драйвера.

### Классификация ошибок

| Ошибка                                                      | Класс                                                                             |
|-------------------------------------------------------------|-----------------------------------------------------------------------------------|
| `jetstream.ErrNoStreamResponse`, `nats.ErrNoResponders`     | **Permanent** — субъекту не соответствует ни один стрим; повтор ничего не изменит |
| `jetstream.ErrInvalidJSAck`, превышение `max_msg_size`      | **Permanent**                                                                     |
| `nats.ErrConnectionClosed`, `nats.ErrConnectionDraining`    | **Unavailable**                                                                   |
| `context.DeadlineExceeded` при живом родительском контексте | **Unavailable**                                                                   |
| остальное                                                   | retryable                                                                         |

### Подвох, который надо решить осознанно

`nats.go` **переподключается сам и буферизует публикации, пока соединения нет**
(`ReconnectBufSize`, по умолчанию 8 МБ). Для обычного приложения это удобство; для диспетчера это опасно: публикация
может «удаться» локально, попав в буфер клиента, и строка станет `sent`, хотя брокер сообщения не видел.

Решение: **буфер выключить** — `nats.ReconnectBufSize(-1)`. Тогда публикация при отсутствии соединения возвращает
ошибку, она классифицируется как `Unavailable`, и работает вся уже построенная машинерия: сообщение откладывается без
траты попытки, предохранитель останавливает claim'ы, `outbox_stream_paused` встаёт в единицу. Переподключение самой
библиотеки при этом остаётся — оно полезно, в отличие от буфера.

Это первое, что надо проверить тестом через ломающийся прокси.

### Конфигурация

```
OUTBOX_DRIVER_<NAME>_TYPE=nats
OUTBOX_DRIVER_<NAME>_DSN=nats://user:pass@host:4222
OUTBOX_DRIVER_<NAME>_STREAM=EVENTS        # имя стрима JetStream
OUTBOX_DRIVER_<NAME>_PUBLISH_TIMEOUT=15s
OUTBOX_DRIVER_<NAME>_PREFIX=...           # общий Naming, как у остальных
```

`Endpoint()` возвращает DSN без учётных данных — как
[`redactDSN`](../internal/config/broker.go) у RabbitMQ.

Открытый вопрос: **создавать ли стрим**. У RabbitMQ есть `DECLARE`; у JetStream аналог — `CreateOrUpdateStream`.
Предлагается по умолчанию **не создавать**:
конфигурация стрима (retention, реплики, `duplicate_window`) — решение владельца кластера, а не сайдкара. Отсутствующий
стрим при этом обязан быть
`Permanent`, чтобы опечатка в субъекте не откладывалась вечно.

### Тесты

- `docker-compose.yml`: `nats:2-alpine` с `-js`, плюс сервис в CI.
- Круговой: publish → consume, заголовки и `Nats-Msg-Id` целы.
- Через прокси: разрыв → `Unavailable` → возврат без траты попытки → восстановление.
- Несуществующий стрим → `Permanent`, сообщение сразу в `failed`.
- Дедупликация: две публикации одного id внутри окна → одно сообщение в стриме.

## 3. Redis Streams

**Не делать — или делать с явной оговоркой в публичном контракте.**

**Размер: +6.33 МБ** (28.20 МБ) — дороже всех кандидатов, вчетверо дороже NATS. Причина: `go-redis` несёт полную
поверхность команд Redis, и линковщик не может её выбросить, потому что это методы достижимого типа. В неурезанной
сборке линкуется 11 160 символов пакета.

### Почему это плохо ложится

`XADD` возвращает id синхронно — с этой стороны всё в порядке. Проблема глубже, и она в самом обещании сервиса.

Диспетчер обещает: **строка становится `sent` только после того, как брокер сказал, что сообщение у него**. У RabbitMQ
это publisher confirm после записи на диск, у Kafka — `acks=all`, у JetStream — подтверждение стрима. У Redis по
умолчанию `appendfsync everysec`: подтверждённый `XADD` может быть потерян при падении процесса в пределах последней
секунды. То есть на Redis то же самое предложение становится слабее, и слабее ровно в той части, ради которой паттерн
transactional outbox вообще существует.

Второе: `MAXLEN`/`XTRIM` могут удалить записи, которых никто не потреблял. Брокер, способный молча выбросить принятое
сообщение, — странный адресат для сервиса, чья единственная задача не терять сообщения.

### Если всё же делать

Тогда обязательно и явно:

- В [`docs/PublicContract.md`](PublicContract.md) — отдельный абзац о том, что с этим драйвером «подтверждено» означает
  «принято Redis», а не «сохранено на диск», и что гарантия зависит от `appendfsync`.
- Проверять на старте `appendonly` и `appendfsync` через `CONFIG GET` и **писать предупреждение в лог**, если это не
  `always`. Молчаливое ослабление гарантии хуже, чем её отсутствие.
- Отдельно взвесить +6.33 МБ. Пункт README «скучен в эксплуатации» держится на размере образа, и 29 → 35 МБ — заметная
  его часть.

Рекомендация: подождать, пока попросят, и тогда спросить, почему именно Redis Streams, а не NATS. Часто ответ «Redis у
нас и так есть» — а он не про доставку.

## 4. SQS/SNS

**По запросу, как и написано в роадмапе.**

**Размер: +3.24 МБ** (25.11 МБ), пятнадцать модулей — AWS SDK v2 модульный, поэтому дешевле своей репутации, но
пятнадцать записей в `go.mod` это пятнадцать записей.

Ложится хорошо: `SendMessage` синхронно подтверждает, `SendMessageBatch` берёт до десяти сообщений и возвращает
`Successful`/`Failed` по позициям — то есть прямо в форму контракта. Классификация: `InvalidMessageContents`,
`UnsupportedOperation` → `Permanent`; таймауты, троттлинг, `ServiceUnavailable`, сетевые ошибки → `Unavailable`.

Отдельная сложность, которой нет у остальных: **аутентификация**. Цепочка провайдеров AWS (переменные окружения,
профиль, IRSA, IMDS) не описывается одним DSN, а весь конфиг этого проекта — плоские переменные `OUTBOX_*`. Предлагается
не изобретать своего: полагаться на стандартную цепочку SDK и держать в конфигурации только регион и URL очереди.

Не делать, пока не попросят: цена не в мегабайтах, а в пятнадцати модулях, за чьими CVE придётся следить ради драйвера,
которым, возможно, никто не воспользуется.

## Предлагаемый порядок

1. **Клиент на `database/sql`** — ноль стоимости, расширяет круг тех, кто может писать в outbox. Вечер работы.
2. **NATS JetStream** — самый дешёвый брокер и лучше всех ложащийся на контракт. Заодно доказывает, что
   `broker.Publisher` не зря вынесен в интерфейс: если третий драйвер не потребует его менять, значит, абстракция верна.
3. **SQS** — когда попросят.
4. **Redis Streams** — когда попросят и объяснят зачем.
