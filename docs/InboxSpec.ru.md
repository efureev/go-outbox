# Инбокс: юзкейсы и верхнеуровневое ТЗ

Как выглядит доставка в PostgreSQL — куда идут данные, что описывает диспетчер, а
что остаётся за потребителем.

Вопрос «а нужно ли это вообще» разобран отдельно, в
[PostgresDestination](PostgresDestination.ru.md): там вердикт, цена и главное
ограничение (fan-out нет). Здесь — как это устроено, если делать.

**Драйвер реализован** — тип `postgres`, формы B и C с дедупликацией на приёме.
Пример схемы инбокса лежит в
[migrations/inbox/messages.sql](../migrations/inbox/messages.sql), переменные — в
[Config](Config.ru.md#доставка-в-таблицу-вместо-брокера).

Не реализована форма A с общей транзакцией: она требует смены контракта
`broker.Publisher` и вынесена в отдельную работу — см. «Что осталось решить».

## Юзкейсы

Развёрнутые рецепты, готовые к копированию, лежат отдельно:

- [Модульный монолит: инбокс вместо брокера](usecases/7-inbox-monolith.ru.md) —
  форма A, ограниченные контексты в одной базе, брокера нет вовсе.
- [Два сервиса, две базы, брокера нет](usecases/8-inbox-two-services.ru.md) —
  форма C, с разделом о цене: инверсия владения.
- [Мёртвые письма в таблицу, а не в топик](usecases/9-dlq-table.ru.md) —
  работает без единой правки в коде.

Побочные выгоды, у которых нет собственного рецепта, потому что они не про
развёртывание: локальный контур и CI без брокера (описано в рецепте 7) и путь
внедрения — начать на PostgreSQL и сменить одну переменную окружения, когда
понадобится брокер.

**Чего этими сценариями не сделать: один продюсер, несколько потребителей.**
Fan-out нет — инбокс точка-точка. Чтобы событие попало к трём потребителям,
продюсер должен записать три строки, то есть перечислить их поимённо. Там, где
нужен веер, PostgreSQL как адресат — неверный выбор.

## Как идут данные

### Что меняется у продюсера: ничего

Во всех трёх формах приложение делает ровно то же, что и сегодня: пишет строку
в outbox внутри своей бизнес-транзакции — и на этом заканчивает. Оно не знает
ни про инбокс, ни про схему потребителя, ни про то, уедет ли сообщение в
таблицу, в RabbitMQ или завтра в Kafka. Адресат — это переменная окружения
диспетчера, а не строка кода приложения.

Поэтому **«одна транзакция» ниже — везде транзакция диспетчера**, та, в которой
он записывает результат доставки. Транзакция продюсера в ней не участвует и не
может: она закоммичена задолго до того, и ровно поэтому outbox и нужен. Продюсер,
вставляющий сразу и в инбокс, — это не форма A, а нарушение границ, ради
устранения которого паттерн и существует.

### Общая схема

```
транзакция продюсера              go-outbox                 база потребителя
┌────────────────────┐    ┌──────────────────────┐    ┌────────────────────┐
│ UPDATE accounts …  │    │ захват (SKIP LOCKED, │    │ INSERT в inbox     │
│ INSERT в outbox    │───▶│         lease-токен) │───▶│ ON CONFLICT (id)   │
│ COMMIT             │    │ вставка в inbox      │    │   DO NOTHING       │
└────────────────────┘    │ запись результата    │    └─────────┬──────────┘
                          └──────────────────────┘              │
                                                                ▼
                                                      потребитель читает
                                                      свою таблицу и
                                                      обрабатывает её сам
```

Слева и посередине не меняется ничего: продюсер пишет ту же строку тем же
клиентом, диспетчер делает тот же захват с тем же lease-токеном. Меняется только
правый блок — вместо `basic.publish` там `INSERT`.

### Форма A: одна база, одна транзакция диспетчера

```
                          одна база PostgreSQL
┌──────────────────────────────────────────────────────────────────┐
│   схема outbox                        схема billing              │
│   ┌───────────────┐                   ┌───────────────┐          │
│   │   messages    │                   │     inbox     │          │
│   └───────┬───────┘                   └───────▲───────┘          │
└───────────┼───────────────────────────────────┼──────────────────┘
            │    go-outbox: одна транзакция     │
            │      ┌────────────────────┐       │
            └─────▶│ BEGIN              │───────┘
                   │   INSERT в inbox   │
                   │   UPDATE status=2  │
                   │ COMMIT             │
                   └────────────────────┘
                              │
        либо обе записи видны, либо ни одной → exactly-once
```

Дедупликация здесь не нужна: состояния «доставлено, но не отмечено» не
существует.

### Формы B и C: две базы, две транзакции диспетчера

```
   база потребителя                          база продюсера
   ┌──────────────────┐
   │ BEGIN            │
   │   INSERT в inbox │
   │ COMMIT           │
   └────────┬─────────┘
            │
            ├──◀── здесь реплика может умереть
            │
            └────────────────────────────▶ ┌───────────────────┐
                                           │ BEGIN             │
                                           │   UPDATE status=2 │
                                           │ COMMIT            │
                                           └───────────────────┘

   падение между коммитами → строка остаётся pending → повторная доставка
   → ON CONFLICT (id) DO NOTHING гасит дубликат
   → at-least-once на проводе, ровно один раз по эффекту
```

Это тот же зазор, что и с любым брокером. Разница в том, что закрывает его не
потребитель своим кодом, а первичный ключ.

### DLQ в таблицу

```
                            ┌──────────────▶ RabbitMQ        (стрим events)
   outbox.messages ──▶ go-outbox
                            └──────────────▶ ops.dead_letter (стрим dlq,
                                              драйвер postgres)
```

Маршрутизация та же, что и между двумя брокерами: стрим выбирает драйвер.

## Контракт инбокса

Таблицу создаёт **потребитель**, не диспетчер. Ровно по той же причине, по
которой драйвер не создаёт стримы JetStream: форма и жизненный цикл таблицы —
решение её владельца.

```sql
CREATE TABLE billing.inbox
(
    -- Пишет диспетчер. Только INSERT, никогда UPDATE и никогда SELECT.
    id          UUID PRIMARY KEY,   -- id строки outbox; на нём и держится дедуп
    stream      TEXT        NOT NULL,
    topic       TEXT        NOT NULL,   -- эффективное имя: с префиксом и версией
    payload     BYTEA       NOT NULL,
    headers     JSONB       NOT NULL DEFAULT '{}'::jsonb,
    received_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    -- Дальше — колонки потребителя. Диспетчер о них не знает.
    processed_at TIMESTAMPTZ,
    attempts     INTEGER NOT NULL DEFAULT 0
);
```

Граница проходит по горизонтальной черте и она принципиальна:

- **Диспетчер только вставляет.** Не читает, не обновляет, не удаляет. Он не
  знает, обработано сообщение или нет, и знать не должен.
- **`id` — это id строки outbox.** Тот же идентификатор, который сегодня едет в
  `MessageId` у AMQP и в заголовке `message_id` у Kafka. Первичный ключ делает
  повторную вставку безвредной.
- **`topic` — эффективное имя**, уже с префиксом и суффиксом версии, то есть то
  же, на что подписывается потребитель у брокера. Правила именования не меняются.
- **Всё, что правее черты, — дело потребителя.** Захват, повторы, чистка. Мы не
  поставляем ни цикла обработки, ни lease, ни фреймворка: роадмап отказывается от
  потребления, и этот отказ остаётся в силе.

Опционально — триггер `NOTIFY` на инбоксе, зеркало миграции `0003`, чтобы
потребитель просыпался на вставку, а не опрашивал таблицу. Поставляется файлом,
который применяет владелец таблицы.

## Конфигурация

Стрим выбирает драйвер, как и сейчас; новый тип — `postgres`.

```bash
OUTBOX_STREAMS=events,billing

# Обычный брокерный стрим — не меняется.
OUTBOX_STREAM_EVENTS_DRIVER=rmq
OUTBOX_DRIVER_RMQ_TYPE=rabbitmq
OUTBOX_DRIVER_RMQ_DSN=amqp://user:pass@rabbit:5672/

# Стрим, который уходит в таблицу.
OUTBOX_STREAM_BILLING_DRIVER=inbox_billing
OUTBOX_DRIVER_INBOX_BILLING_TYPE=postgres
OUTBOX_DRIVER_INBOX_BILLING_DSN=            # пусто = база самого диспетчера
OUTBOX_DRIVER_INBOX_BILLING_SCHEMA=billing
OUTBOX_DRIVER_INBOX_BILLING_TABLE=inbox
```

**Пустой `DSN` — это и есть форма A.** Он означает «та же база, что у
диспетчера», то есть тот же пул, то же соединение и принципиальная возможность
одной транзакции диспетчера. Заполненный DSN — формы B и C, отдельный пул и дедупликация на
приёме. Три формы выражаются одной переменной, и это стоит того, чтобы так и
сделать.

`Endpoint()` обязан возвращать DSN без учётных данных: он отдаётся наружу через
`GET /api/v1/stats`.

## Что делает диспетчер и чего не делает

| Делает | Не делает |
|---|---|
| Вставляет пачкой, одним запросом | Не создаёт таблицу |
| Гасит дубликат через `ON CONFLICT` | Не читает и не обновляет инбокс |
| Проверяет наличие таблицы на старте | Не удаляет обработанное |
| Применяет те же правила именования | Не поставляет цикл обработки |
| Отдаёт те же метрики и спаны | Не делает fan-out |

Проверка таблицы на старте — то же правило, что и для брокеров: недоступный
адресат валит запуск, а не обнаруживается на первом сообщении.

## Ретеншен: инбокс чистит потребитель

Наш janitor чистит **свою** таблицу — outbox. Инбокс он не трогает и трогать не
будет: диспетчер в него только вставляет.

Это значит, что **таблица будет расти, пока её владелец не начнёт её чистить**, и
расти молча — ни метрики, ни лога с нашей стороны не появится, потому что мы туда
не смотрим. Сказано здесь прямо именно поэтому: единственный отказ этого драйвера,
который проявляется не сразу, а через полгода, — забытая уборка.

Чистит потребитель, и он же решает, что значит «обработано»:

```sql
-- Простейший вариант: удалять обработанное старше недели.
DELETE FROM billing.inbox
 WHERE processed_at IS NOT NULL
   AND processed_at < now() - interval '7 days';
```

Порциями, если таблица большая, — по той же причине, по которой это делает наш
janitor: одна безразмерная `DELETE` держит транзакцию открытой и раздувает ту
таблицу, которую пытается уменьшить.

```sql
DELETE FROM billing.inbox
 WHERE id IN (
     SELECT id FROM billing.inbox
      WHERE processed_at IS NOT NULL
        AND processed_at < now() - interval '7 days'
      ORDER BY received_at
      LIMIT 5000
      FOR UPDATE SKIP LOCKED);
```

За теми же объёмами, за которыми мы партиционируем outbox, инбокс стоит
партиционировать по `received_at` — и тогда уборка становится `DROP TABLE`, как и
у нас. Рассуждение целиком —
[в Эксплуатации](Operations.ru.md#партиционирование-начиная-примерно-с-десяти-миллионов-строк-в-сутки).

## Размер сообщения: предела нет

У каждого брокерного драйвера есть перманентный класс отказа «payload больше
лимита» — размер фрейма у RabbitMQ, `message.max.bytes` у Kafka. **У этого
драйвера такого класса нет.**

Это измерено, а не предположено: 32 МиБ одним сообщением и 64 МиБ одним батчем
проходят и возвращаются байт в байт. Документированный потолок PostgreSQL — 1 ГБ
на поле; до него интеграционные тесты не доходят, и утверждать про него что-либо
из замеров нельзя.

Практический вывод: сообщение, которое брокер отверг бы навсегда, в инбокс
проходит. Если это нежелательно, ограничение ставит потребитель — `CHECK
(length(payload) < …)` на своей таблице, и тогда оно вернётся как `Permanent`,
как любой другой отказ схемы.

## Отказы и их классы

Классификация — самое ответственное решение в любом драйвере; ошибка в сторону
`Unavailable` дороже всего, потому что такое сообщение никогда не увеличит
счётчик попыток и никогда не дойдёт до `failed`.

| Ситуация | Класс | Почему |
|---|---|---|
| `ON CONFLICT` вернул ноль строк | **успех** | Сообщение уже доставлено — это и есть дедупликация |
| База недоступна, отказ соединения | `Unavailable` | Ляжет на отложенную доставку без траты попытки |
| Таблицы не существует | `Permanent` | Повтор её не создаст |
| Нарушение `NOT NULL` или `CHECK` | `Permanent` | Сообщение не подходит этой таблице, и завтра тоже не подойдёт |
| Deadlock, serialization failure | retryable | Повтор помогает, попытку тратим |
| `statement_timeout` | `Unavailable` | Скорее перегрузка базы, чем проблема сообщения |

Последняя строка — решение, а не факт; её стоит подтвердить на реальной нагрузке,
прежде чем закреплять.

## Exactly-once формы A: решено не делать

Единственный пункт, который оставался открытым, закрыт отказом.

Идея была в том, чтобы вставка в инбокс и пометка строки `sent` попали в одну
транзакцию диспетчера — тогда состояния «доставлено, но не отмечено» не
существует вовсе.

**Выгода оказалась меньше, чем кажется.** Первичный ключ инбокса уже даёт «ровно
один раз по эффекту»: повтор гасится, дубликата в таблице не возникает. Одна
транзакция убирает не дубликат — его и так нет, — а лишь окно, в котором доставка
уже произошла, а строка ещё `pending`. Наблюдаемое отличие: без транзакции
возможна лишняя вставка, которую `ON CONFLICT` отбрасывает.

**Цена оказалась больше.** Интерфейс `broker.Publisher` менять не пришлось бы —
правильная форма была бы необязательным вторым интерфейсом, как `io.ReaderFrom`,
— но за ним тянулось:

- `pgx.Tx` в `internal/broker`, то есть слой абстракции над брокерами начинает
  знать про конкретную базу;
- вторая ветка в `RunOnce` — самом горячем коде проекта;
- `SAVEPOINT` на каждое сообщение на пути отказа, потому что в PostgreSQL любая
  ошибка отравляет транзакцию целиком;
- выключенный параллелизм публикации: одну транзакцию нельзя использовать из
  нескольких горутин, и `OUTBOX_DISPATCH_WORKERS` для такого стрима перестал бы
  что-либо значить;
- новый инвариант: число затронутых `Ack` строк надо проверять **до** коммита,
  иначе перехваченный lease оставит вставку в инбоксе закоммиченной.

Решение принято: не делать, пока не появится потребитель, которому мало
дедупликации по первичному ключу. Формулировка в
[публичном контракте](PublicContract.ru.md) остаётся честной — at-least-once на
проводе, идемпотентность на приёме, — и она обеспечена схемой, а не обещанием.
