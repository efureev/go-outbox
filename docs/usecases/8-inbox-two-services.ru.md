# Два сервиса, две базы, брокера нет

[English](8-inbox-two-services.md) | Русский

Назад к [указателю сценариев](../UseCases.ru.md).

Сервис заказов доставляет события в инбокс сервиса биллинга. У каждого своя база,
между ними нет ничего — ни RabbitMQ, ни Kafka. Классическая пара outbox/inbox без
посредника.

Прежде чем копировать: **сначала прочитайте раздел «Чем платим»**. У этого
сценария есть цена, которая во многих организациях закрывает вопрос, и лучше
узнать о ней здесь, чем на ревью.

### Инбокс — на стороне потребителя

Таблицу создаёт биллинг, в своей базе, своей миграцией. Полный пример —
[migrations/inbox/messages.sql](../../migrations/inbox/messages.sql).

```sql
CREATE TABLE inbox.orders
(
    id      UUID PRIMARY KEY,
    stream  TEXT  NOT NULL,
    topic   TEXT  NOT NULL,
    payload BYTEA NOT NULL,
    headers JSONB NOT NULL DEFAULT '{}'::jsonb,
    received_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at TIMESTAMPTZ
);
```

Роль, которой пользуется диспетчер заказов, должна уметь ровно одно:

```sql
CREATE ROLE orders_dispatcher LOGIN PASSWORD '…';
GRANT USAGE          ON SCHEMA inbox TO orders_dispatcher;
GRANT INSERT, SELECT ON inbox.orders TO orders_dispatcher;
-- И ничего больше: ни UPDATE, ни DELETE.
```

**`SELECT` здесь обязателен, и это не описка.** Драйвер только вставляет, но
делает это через `ON CONFLICT (id) DO NOTHING`, а PostgreSQL требует права на
чтение таблицы, когда у `ON CONFLICT` указана цель конфликта. Проверено: с одним
`INSERT` вставка проходит, а та же вставка с `ON CONFLICT (id)` падает с
`42501 permission denied`.

Форма без указания цели — `ON CONFLICT DO NOTHING` — обошлась бы одним `INSERT`,
и мы её сознательно не используем: она гасит **любое** нарушение уникальности, а
не только повтор по `id`. Сообщение с новым `id`, но занятым бизнес-ключом, тогда
исчезло бы молча и было бы отчитано как доставленное. Проверено тем же
экспериментом. Более широкий грант — меньшее из двух зол: потерянное сообщение
хуже, чем право на `SELECT`.

### Конфигурация диспетчера заказов

```dotenv
OUTBOX_DB_DSN=postgres://orders:secret@orders-db:5432/orders?sslmode=require
OUTBOX_STREAMS=billing

OUTBOX_STREAM_BILLING_DRIVER=inb
OUTBOX_DRIVER_INB_TYPE=postgres
OUTBOX_DRIVER_INB_DSN=postgres://orders_dispatcher:secret@billing-db:5432/billing?sslmode=require
OUTBOX_DRIVER_INB_SCHEMA=inbox
OUTBOX_DRIVER_INB_TABLE=orders
OUTBOX_DRIVER_INB_PREFIX=orders
```

`PREFIX` здесь полезен: в колонке `topic` окажется `orders.order.paid`, и по
источнику события можно фильтровать, не заводя отдельной колонки.

Учётные данные видны в `GET /api/v1/stats` **без пароля** — эндпоинт вырезает его
и показывает адресата вместе с таблицей:

```json
{ "name": "inb", "type": "postgres",
  "endpoint": "postgres://billing-db:5432/billing?sslmode=require#inbox.orders" }
```

### Что получается по гарантиям

Доставка **at-least-once**, как и с любым брокером: вставка в инбокс и пометка
строки outbox как `sent` — два коммита в двух разных базах, и реплика может
умереть между ними.

Разницу делает первичный ключ. Повтор гасится вставкой `ON CONFLICT (id) DO
NOTHING`, и драйвер считает конфликт доставкой — сообщение в инбоксе либо так,
либо иначе. **Дедупликация перестаёт быть обязанностью кода биллинга и становится
свойством его схемы.**

### Чем платим

**Инверсия владения.** Диспетчер заказов получает права на запись в базу
биллинга. Во многих организациях это закрывает вопрос само по себе, и спорить с
этим бессмысленно — регламент есть регламент.

Смягчающие обстоятельства, если разговор всё-таки идёт:

- Интерфейс узкий: одна таблица, только `INSERT`, форма фиксирована и
  задокументирована. Это, пожалуй, более узкий контракт, чем общий топик в
  брокере, где обе стороны договариваются о схеме сообщения и ни одна не может
  её проверить.
- Грант проверяем: `GRANT INSERT, SELECT` и ничего больше — ни `UPDATE`, ни
  `DELETE`. Чтение нужно самому `ON CONFLICT`, а не нам: диспетчер не выполняет
  ни одного `SELECT` по этой таблице.
- Но кредиты, сетевой доступ между базами и согласованная между двумя командами
  миграция никуда не деваются.

**Fan-out нет.** Инбокс — точка-точка. Третий потребитель означает третий стрим и
третью строку от продюсера. Если веер нужен — нужен брокер, и этот сценарий не
подходит.

### Что здесь ломается

- **Сеть между базами.** Недоступный инбокс — это `Unavailable`: сообщения
  откладываются **без траты попытки**, предохранитель останавливает захваты для
  этого стрима, `outbox_stream_paused` встаёт в единицу. Ничего не теряется и
  ничего не уходит в `failed` — ровно то же поведение, что и с упавшим брокером.
- **Миграция биллинга, снявшая колонку.** `42703 undefined_column` — это
  `Permanent`: сообщения сразу в `failed`, видны в `outbox failed`. Так и надо:
  повтор колонку не вернёт. Но это значит, что миграции инбокса должны быть
  обратно совместимыми ровно так же, как схема сообщения в брокере.
- **Отозванный грант.** `42501 insufficient_privilege` — тоже `Permanent`, по той
  же причине.
- **Забытая уборка.** Инбокс чистит биллинг. Диспетчер заказов туда не смотрит и
  не сообщит, что таблица растёт.
- **`sslmode=disable` между базами.** Внутри одного хоста это выбор, между
  хостами — сообщения и учётные данные открытым текстом.
