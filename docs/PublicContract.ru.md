# Публичный контракт

[English](PublicContract.md) | Русский

Этот документ описывает границу между продюсером и диспетчером: что пишет продюсер, чем владеет диспетчер, как
маршрутизируется сообщение и что осознанно не обещается.

Всё описанное здесь версионируется. Всё, чего здесь нет — внутренние колонки, набор индексов, тексты SQL, имена метрик —
может меняться без предупреждения.

## 1. Таблица

**`<схема>.<таблица>`**, по умолчанию `outbox.messages`, в PostgreSQL.

### 1.1 Что пишет продюсер

| Колонка        | Тип           | Обяз. | Смысл                                                                                                                                                                                                                                             |
|----------------|---------------|-------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `id`           | `UUID`        | да    | Идентичность сообщения. Генерируйте UUIDv7: он сортируется по времени создания, поэтому индекс первичного ключа остаётся append-упорядоченным, а не разбрасывает записи по всему дереву. Это же значение потребитель использует для дедупликации. |
| `stream`       | `TEXT`        | да    | Логическое направление. Должно называть сконфигурированный стрим.                                                                                                                                                                                 |
| `topic`        | `TEXT`        | да    | Логический топик или очередь — **без** префикса и суффикса версии.                                                                                                                                                                                |
| `payload`      | `BYTEA`       | да    | Доставляется брокеру байт в байт. Диспетчер в него не заглядывает.                                                                                                                                                                                |
| `headers`      | `JSONB`       | нет   | Плоский объект «строка → строка», доставляется как заголовки брокера. Положите сюда `traceparent`, чтобы потребитель продолжил ваш трейс.                                                                                                         |
| `target`       | `JSONB`       | нет   | Конверт маршрутизации; см. §2.                                                                                                                                                                                                                    |
| `available_at` | `TIMESTAMPTZ` | нет   | Откладывает первую попытку. По умолчанию — сейчас.                                                                                                                                                                                                |

У всех остальных колонок есть серверные значения по умолчанию, и принадлежат они диспетчеру. Указание такой колонки в
INSERT — это ровно тот путь, которым продюсер записывает статус или lease, устанавливать которые он не должен.

Запись обязана происходить **в той же транзакции, что и бизнес-изменение**. В этом весь паттерн: запись через отдельное
соединение означает, что сообщение может быть опубликовано для изменения, которое откатили, или потеряно для изменения,
которое зафиксировали.

```sql
BEGIN;
UPDATE accounts
SET balance = balance - 100
WHERE id = 42;
INSERT INTO outbox.messages (id, stream, topic, payload, headers, target)
VALUES (gen_random_uuid(), 'local', 'account.debited',
        convert_to('{"account":42,"amount":100}', 'UTF8'),
        '{"traceparent":"00-…-01"}'::jsonb,
        '{"key":"42"}'::jsonb);
COMMIT;
```

Из Go используйте [`pkg/outboxclient`](../pkg/outboxclient) на pgx или
[`pkg/outboxsql`](../pkg/outboxsql) на `database/sql`. Оба принимают транзакцию аргументом, поэтому
транзакционность перестаёт быть тем, о чём нужно помнить, и ни один нельзя применить правильно без неё.

### 1.2 Возврат упавшего сообщения в очередь

Единственный поддерживаемый способ, доступный из трёх мест:

```sql
SELECT outbox.requeue(ARRAY['…', '…']::uuid[]);
SELECT outbox.requeue_failed_before(now() - interval '1 day', 1000);
```

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" \
  http://outbox:8085/api/v1/messages/requeue \
  -d '{"ids":["…"]}'
```

Не пишите собственный UPDATE. Возврат в очередь обязан вместе со статусом
сбросить счётчик попыток и время доступности; неполная версия такого UPDATE даёт
строку, которая формально pending, но никогда больше не будет выбрана, — а это
отказ куда более тихий, чем была бы ошибка.

### 1.3 Колонки, которыми владеет диспетчер

Читать для наблюдаемости можно, писать — нельзя.

| Колонка                               | Смысл                                                            |
|---------------------------------------|------------------------------------------------------------------|
| `status`                              | `0` pending, `1` processing, `2` sent, `3` failed.               |
| `attempts`                            | Сколько раз брокер отверг сообщение. Не растёт, если до брокера не достучались. |
| `lease_token`, `lease_until`, `owner` | Текущий захват: какая реплика держит строку и до какого момента. |
| `last_error`                          | Почему упала последняя попытка.                                  |
| `created_at`                          | Проставляется базой.                                             |
| `dispatched_at`                       | Когда брокер принял сообщение.                                   |
| `deferred_since`                      | Когда сообщение впервые отложили из-за недоступного брокера. `NULL`, если ждать нечего. |

Два инварианта обеспечены схемой, а не соглашением: строка находится под lease ровно тогда, когда обрабатывается, и
`attempts` никогда не отрицателен.

## 2. Маршрутизация

### 2.1 `target`

| Ключ          | Тип     | Смысл                                                              |
|---------------|---------|--------------------------------------------------------------------|
| `key`         | string  | Ключ партиционирования. Kafka его использует, RabbitMQ игнорирует. |
| `version`     | integer | При значении больше нуля добавляет к имени топика суффикс `vN`.    |
| `exchange`    | string  | AMQP exchange. Пусто — exchange по умолчанию.                      |
| `routing_key` | string  | AMQP routing key. Пусто — имя топика.                              |

Неизвестные ключи сохраняются и игнорируются. Это точка расширения.

### 2.2 Эффективное имя

```
эффективное = [prefix + prefix_sep] + topic + [version_sep + "v" + version]
```

Префикс и разделители берутся из конфигурации драйвера. **Потребитель подписывается на эффективное имя**, а не на
значение колонки `topic`: при
`OUTBOX_DRIVER_RMQ_PREFIX=prod` и `topic = 'user.created'` очередь называется
`prod_user.created`.

`GET /api/v1/stats` отдаёт префикс и разделители каждого драйвера, так что эффективное имя можно вывести, не читая чужой
конфигурационный файл.

## 3. Семантика доставки

| Статус     | Кто выставляет      | Смысл                                                                        |
|------------|---------------------|------------------------------------------------------------------------------|
| pending    | продюсер, диспетчер | Готово, как только пройдёт `available_at`.                                   |
| processing | диспетчер           | Захвачено, под lease.                                                        |
| sent       | диспетчер           | Брокер подтвердил приём. Терминальный.                                       |
| failed     | диспетчер           | Попытки исчерпаны либо permanent-ошибка. Терминальный до возврата в очередь. |

**At-least-once.** Закоммиченное сообщение будет опубликовано. Оно может быть опубликовано более одного раза: реплика
способна упасть между приёмом сообщения брокером и записью этого факта в базу. Потребители обязаны быть идемпотентными,
и для этого каждое сообщение несёт свой outbox-идентификатор — `MessageId` в AMQP, заголовок `message_id` в Kafka.

**Публикация с подтверждением.** Строка становится `sent` только после того, как брокер сообщил, что сообщение у него:
publisher confirm в AMQP, `acks=all` в Kafka по умолчанию.

**Permanent-ошибки не тратят бюджет повторов.** Недоставляемое сообщение, неизвестный стрим, payload сверх лимита
брокера или отклонённые учётные данные падают сразу, а не тратят пять попыток и час backoff'а на переоткрытие того же
факта.

**Бюджет повторов считает отказы, а не минуты.** Недоступный брокер сообщения не видел, поэтому оно за него не платит:
строка возвращается в `pending` с нетронутым счётчиком попыток и повторяется, пока брокер не вернётся. Авария не съедает
бюджет и не заканчивается статусом `failed` — если только не задан `OUTBOX_DISPATCH_MAX_DEFER`, который ограничивает
такое ожидание.

## 4. Что не гарантируется

- **Порядок.** Реплики публикуют параллельно, воркеры внутри реплики — тоже, а переотправленное сообщение уходит позже
  написанных после него. Потребителям, которым нужен порядок в пределах ключа, придётся обеспечить его самим.
- **Латентность.** При включённых уведомлениях доставка обычно укладывается в десятки миллисекунд, при выключенных —
  ограничена интервалом опроса. Ни то ни другое не является SLA. Метрика, по которой имеет смысл спрашивать, —
  `outbox_oldest_pending_age_seconds`.
- **Хранение.** Доставленные строки удаляются через
  `OUTBOX_JANITOR_RETENTION`. Не используйте эту таблицу как журнал событий.
- **Уникальность.** Две строки с одинаковым payload — это два сообщения. Дедупликация, если она нужна, — ответственность
  продюсера, по ключу `id`.

## 5. Версионирование

Контракт покрывает колонки продюсера (§1.1), возврат в очередь (§1.2), ключи
`target` и правило именования (§2), статусы и гарантии (§3), а также форму задокументированных HTTP-ответов.

Несовместимое изменение любого из этих пунктов — мажорная версия, отдельно отмеченная в release notes.
